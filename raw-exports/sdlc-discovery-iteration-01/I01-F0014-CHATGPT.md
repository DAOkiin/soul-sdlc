## Что ты на самом деле сделал (по приложенным файлам)

У тебя это не абстрактная идея, а довольно конкретная система:

- **DDL процесса** (граф шагов + переходы) в YAML/JSON-совместимом виде.\
  Пример: `scope_gate` → ветка **A/B/C** → соответствующий “путь” → `validation_gate` (terminal).
- **Runtime state** в файле: `current_step`, `status`, `branch`, `memory`, `history`.
- **Компилятор/валидатор процесса**:
  - проверяет достижимость шагов,
  - проверяет что есть terminal,
  - что terminal без исходящих переходов,
  - что все transition targets существуют.
- **CLI**: `init / advance / show / compile`.
- **Скрипт “print\_project\_state”**, который тянет:
  - git-ветку/коммит/dirty,
  - итерацию и чеклисты (reviews/acceptance/traceability),
  - прогоняет `just test`,
  - и печатает “рекомендуемые первые действия”.

Это уже больше, чем “давайте назовём статусы”. Это похоже на **process-as-code + quality gates + быстрый cockpit**.

## Насколько это “изобретение велосипеда”

### В каком смысле это велосипед

Почти любая “управляемая разработка” в индустрии уже живёт в виде **машины состояний**, просто часто она спрятана в:

- workflow issue-трекера (статусы + переходы + условия),
- CI/CD пайплайне (stages),
- политиках “merge gated by checks”,
- чеклистах ревью.

То есть **концептуально** “процесс = states + transitions” — это прям классика.

### В каком смысле это не просто велосипед

Твоё отличие (и потенциальная ценность) — **где живёт истина и как она проверяется**:

- процесс и правила **в репозитории**, рядом с кодом и артефактами,
- есть валидация графа,
- есть воспроизводимость и история переходов,
- можно встроить в pre-push/CI,
- и самое важное: ты связываешь это с **артефактами SDLC** (чеклисты, acceptance IDs, traceability, QC).

Это уже ближе к **“workflow/policy as code”**, а не просто “статусы в таск-трекере”.

## Оценка по шкалам (с числами)

Я дам оценки отдельно для **идеи** и для **реализации/угла**, потому что это важное различие.

### 1) Инновационность

- **Идея “процесс разработки как state machine”**: **2–4 / 10**\
  (широко известный паттерн, просто часто не называют так явно)
- **Твой угол “процесс + артефакты + валидация + repo-first + CLI/автоматизация”**: **6–7 / 10**\
  (не уникально в мире, но редкость в командах; и особенно редкость — сделать это минималистично и проверяемо)

### 2) Оправданность (ROI / смысл)

Судя по тому, что у тебя уже есть SDLC-док, baselines, QC standard, traceability и т.п., ты явно целишься в **управляемость, доказуемость, сниженный риск “забыли шаг”**.

- **Если у тебя есть гейты типа “изменил доступ к данным → обнови Query Catalog → прогони валидатор”** и это реально боль/риски: **7–9 / 10**
- **Если это маленькая команда/стартап, где важнее скорость, а ошибки дешёвые**: **3–5 / 10** (начнёт съедать внимание)

Ключ: оправданность высокая, когда цена пропуска шага высокая и повторяемость высокая.

### 3) “Стоящее фокуса”

Тут ответ зависит от того, *что именно ты собираешься “фокусить”*.

- **Фокус на инструмент как “лёгкий навигатор/гейт” внутри твоего репо** (минимум состояний, максимум автоматических проверок): **7–8 / 10**
- **Фокус на превращение этого в универсальный движок процессов/продукт**: **2–4 / 10**, *если нет явного product-market fit*\
  (рынок уже забит, и там быстро начинается ад: параллельность, исключения, человеко-ориентированные сценарии, интеграции, UI, миграции процессов…)

## Главный критерий: ты “управляешь людьми” или “управляешь фактами”

Самая опасная развилка:

### Хороший вариант

State machine **фиксирует факты и критерии готовности**:

- какой путь выбран (A/B/C),
- какие проверки обязаны быть зелёными,
- какие артефакты должны существовать,
- что является “definition of done” для шага.

То есть это **навигация + валидация**.

### Плохой вариант

State machine превращается в “командно-административный контроль”:

- 25 статусов,
- ручные переходы ради переходов,
- “по процессу мы на шаге X”, но реальность другая,
- люди начинают “обходить” систему.

---

## Риски (куда обычно ломается такая идея)

1. **Дублирование источника истины**\
   Если таск-трекер говорит одно, state-файл другое, CI третье — начнут не верить ничему.

2. **Merge-конфликты / гонки**\
   Один общий state-файл на репо в командной разработке часто конфликтует.\
   Решение: *state per task/branch/PR* или *derived state*.

3. **Ручная рутина**\
   Если `advance` надо делать руками часто — это начнёт раздражать.\
   Выигрывают системы, где **80% переходов происходят автоматически** по сигналам (PR открыт, тесты прошли, чеклист подписан и т.д.).

4. **Слишком линейная модель**
   Разработка не всегда “строго вперёд”: часто есть rework/возвраты/параллельность.\
   Если это нужно, лучше:
   - либо добавить “rework transitions” (явно),
   - либо считать state machine не “жизнью задачи”, а “жизнью проверки/гейта”.

## Что я бы рекомендовал тебе фокусить (если цель — польза, а не “построить движок”)

### Фокус №1: сделать state максимально **выводимым из репозитория**

Чем больше “состояние” вычисляется из фактов, тем меньше ручной боли.
Примеры:

- `validation_gate` выполнен, если CI зелёный + acceptance/traceability заполнены.
- ветка A/B/C может определяться (частично) по детекту “меняли query-catalog/DDL/контракт”.

### Фокус №2: держать количество шагов маленьким

Твой пример с `scope_gate` и путями A/B/C — хороший: это **один ранний выбор, который реально меняет требования**.\
Вот такие гейты стоят золота.\
А вот “design→implement→test→review→done” — почти всегда уже есть в любом месте.

### Фокус №3: сделать “следующее действие” суперочевидным

То, что твой `print_project_state` уже печатает “Recommended First Actions” — это правильное направление.
Лучшая UX-мера: человек запускает одну команду и понимает, **что делать дальше и почему**.

### Фокус №4: “escape hatch” и честный “blocked”

У тебя уже есть `status: blocked`. Это важно.
Реальность всегда даст ситуации “процесс не покрывает кейс”.

## Дизайн (выбранный подход)

### Почему не встраиваем guards в DDL

DDL уже валидируется pydantic-моделями. Добавление полей “guards” в DDL быстро превратит DDL в “всё обо всём”. Лучше держать:

- DDL = граф,
- Guards = проверки/политики исполнения.

### Формат guards-конфига

Новый файл:

- `docs/_meta/process/sdlc-task-flow.guards.yaml` (JSON‑compatible YAML)

Схема (v0):

- `process_id`, `version` (должны совпасть с DDL)
- `contexts`:
  - `pre_push`: список guards, которые запускаются перед push
  - `advance`: mapping `step_id -> список guards`, которые должны проходить **перед advance** с этого шага (дополнительно, но очень желательная связка)

Guard (минимальный набор типов):

- `command`: выполнить shell‑команду (например `just test`)
- `require_branch`: требовать, чтобы `state.branch` был установлен (A/B/C)
- `glob_exists`: требовать существование файлов по glob (например ADR)

У guard есть:

- `id` (строка)
- `title` (строка)
- `severity`: `error|warn` (warn не блокирует pre-push, но печатается)
- `when`: условия выполнения:
  - `branch_in`: `["A","B","C"]` (опционально)
  - `changed_files_any`: список glob‑паттернов; запускать guard только если **хотя бы один** изменённый файл совпал\
    (нужно для скорости, особенно для QC)

Важно: список изменённых файлов должен приходить из `pre-push` (по диапазону пуша), и пробрасываться в runner и в QC-скрипт через env `QC_CHANGED_FILES`.

## Deliverables (что реализовать)

### 1) Guard runner (CLI tool)

Добавить модуль:

- `src/paip/process_guards.py`

CLI:

- `python -m paip.process_guards check --context pre_push --ddl <...> --state <...> --guards <...> [--changed-files-file <...>]`
- `python -m paip.process_guards check --context advance --ddl ... --state ... --guards ...`\
  (в этом режиме runner должен брать guards для `current_step` и проверять readiness “можно ли advance”)
- (опционально, но рекомендую) `python -m paip.process_guards advance --ddl ... --state ... --guards ... [--to <step>] [--branch <A|B|C>] [--reason "..."]`\
  → делает guard‑check для контекста `advance` и **только потом** вызывает логику advance и сохраняет state.

Поведение runner’а:

- Загружает DDL + state + guards config, проверяет совпадение `process_id/version`.
- Определяет `branch` из `state.branch`.
- Загружает changed files (если есть) из:
  - `--changed-files-file` (каждая строка — путь), иначе из env `PAIP_CHANGED_FILES` (если задан).
- Для каждого guard:
  - проверяет `when` (branch, changed\_files),
  - исполняет guard,
  - пишет результат в человекочитаемом виде (✓ / ✗ / ! skipped),
  - аккуратно печатает хвост stdout/stderr при падении команды (например последние 30–50 строк).
- Exit code:
  - `0`, если нет `severity=error` failure,
  - `1`, если есть хотя бы один error failure.
  - Warn failures не блокируют, но отмечаются.

При выполнении `command` guards:

- пробрасывай env:
  - `PAIP_CHANGED_FILES` (newline-separated)
  - `QC_CHANGED_FILES` (тот же список) — чтобы `scripts/qc_validate_ci.sh` мог скипать/ранить.

### 4) Инструмент визуализации графа (Mermaid)

Расширить `src/paip/process_compiler.py`:

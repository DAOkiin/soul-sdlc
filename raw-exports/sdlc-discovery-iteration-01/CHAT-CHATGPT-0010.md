# 1. Что такое `git worktree`

`git worktree` позволяет:

- иметь **несколько рабочих директорий**
- у одного и того же `.git`
- с разными ветками
- без клонирования репозитория

То есть:

```
repo/
repo-feature-a/
repo-feature-b/
```

Все они используют один `.git`, но работают в разных ветках.

---

# 2. Базовые команды

## 🔹 Добавить новую рабочую директорию

```bash
git worktree add <path> <branch>
```

### Примеры

### 1️⃣ Создать worktree для существующей ветки:

```bash
git worktree add ../feature-auth feature/auth
```

Создаст:

```
../feature-auth
```

и переключит туда ветку `feature/auth`.

---

### 2️⃣ Создать новую ветку и сразу worktree:

```bash
git worktree add -b feature/search-ai ../feature-search
```

- `-b` создаёт новую ветку
- `../feature-search` — новая директория

Это самый удобный вариант для Codex-агентов.

---

## 🔹 Посмотреть список worktree

```bash
git worktree list
```

---

## 🔹 Удалить worktree

```bash
git worktree remove ../feature-search
```

Если ветка больше не нужна:

```bash
git branch -d feature/search-ai
```

```bash
cd ~/dev/project

```

Теперь структура:

```

project-agent-parser/
project-agent-ui/
```

Каждый — отдельная ветка.

---

- File → Open Folder

Каждый агент работает:

- в своей ветке
- в своей директории
- не ломает другие

# 4. Ключевые правила, чтобы всё работало безопасно

## ❗ 1. Не переключай ветки внутри worktree

Каждый worktree "прибит" к своей ветке.

Не делай:

```bash
git checkout main
```

внутри worktree — Git не даст, но лучше не пытаться.

---

## ❗ 2. Никогда не работай в основной папке

Лучше считать `project/`:

- только для создания worktree
- не для разработки

---

## ❗ 3. Каждый агент = отдельная ветка

Никакого:

- два агента в одной ветке
- два агента в одной директории

# 6. Очень важная деталь: как это работает внутри `.git`

Git создаёт:

```
.git/worktrees/<name>/
```

Каждый worktree:

- имеет собственный HEAD
- имеет собственный index
- но общий object storage

Это экономит место и позволяет делать rebase/merge безопасно.

- один агент
- одна ветка

## 1) Что официально говорит OpenAI про worktree в Codex app (macOS)

OpenAI прямо пишет, что **Codex app включает встроенную поддержку worktrees**, чтобы *несколько агентов могли работать с одним репозиторием без конфликтов*: каждый агент работает в **изолированной копии кода**, и ты можешь “подхватывать” изменения локально, не ломая свой текущий git state. citeturn2view0

### Как это работает в самом Codex app (инструкция)

Официальная страница “Worktrees” в Codex docs описывает пошагово:

1. В новом треде выбери режим **Worktree**
2. Выбери стартовую ветку (main/master, фича-ветку или текущую ветку даже с локальными изменениями)
3. Codex создаст git worktree и **по умолчанию работает в detached HEAD** (то есть не “засоряет” твои ветки) citeturn7view0turn9view0

Дальше есть **2 рекомендуемых workflow**, в зависимости от того, как ты хочешь проверять/коммитить изменения:

### Workflow A — работать прямо в worktree (без локального checkout)

- В треде нажимаешь **Create branch here** → превращаешь worktree в ветку → коммитишь/пушишь/делаешь PR.
- IDE можно открыть прямо в worktree кнопкой **Open** (или пользоваться встроенным терминалом). citeturn7view0turn9view0

**Важно:** если ты создал ветку “на worktree”, Git **не даст** чек-аутить эту же ветку где-то ещё (включая твой локальный checkout), пока worktree существует. citeturn9view0

### Workflow B — синхронизировать изменения в твой локальный checkout

- Нажимаешь **Sync with local** и выбираешь: создать новую ветку или синкнуться в существующую.
- Есть два метода:
  - **Overwrite** — делает целевую копию “точь-в-точь” как источник (файлы и история)
  - **Apply** — накладывает “патч” изменений поверх твоей локальной истории (переносит код, но не переносит коммиты источника) citeturn7view0turn9view0

Также в docs отмечено: файлы из `.gitignore` **не переносятся** через sync (что логично: это git-операции). citeturn9view0

### Где физически лежат worktrees Codex app

- Codex создаёт worktrees в **`$CODEX_HOME/worktrees`**. citeturn7view0turn9view0
- `CODEX_HOME` по умолчанию — **`~/.codex`**. citeturn8view0
- И прямо сказано: **выбрать другой путь для worktrees “не сегодня”** — Codex кладёт их под `$CODEX_HOME/worktrees`, чтобы управлять ими консистентно. citeturn9view0

### Про очистку worktrees (важно при многопоточности)

Worktrees могут занимать много места (deps, кэши, сборки), поэтому Codex app пытается ограничивать их количество и чистит автоматически при условиях (например, “старше 4 дней” и “больше 10 worktrees”), но:

- не удаляет, если тред закреплён или worktree добавлен в sidebar,
- перед удалением сохраняет snapshot, который можно восстановить. citeturn9view0

## 2) Та самая git-команда, которая “создаёт копию в директории”

Это **`git worktree add`**.

Официальный `git-worktree` мануал объясняет модель так: репозиторий может иметь **одну main worktree** (если не bare) и **несколько linked worktree**, которые можно добавлять/удалять/листить/чистить. citeturn5view0

### Базовые формы (по git-scm)

```bash
# создать worktree; по умолчанию git может создать новую ветку с именем как у папки
git worktree add <path>

# создать worktree на существующей ветке
git worktree add <path> <branch>

# создать новую ветку и сразу worktree (самый частый вариант)
git worktree add -b <new-branch> <path> <start-point>

# создать "одноразовый" worktree в detached HEAD (удобно для экспериментов/агентов)
git worktree add --detach <path>
```

То, что `add <path>` может автоматически создать новую ветку по имени последнего сегмента пути, и что detached-worktree удобен для экспериментов — прямо описано в мануале. citeturn5view0

## 3) “Правильно” для одного проекта + несколько агентов (рецепт)

### Рекомендованный вариант (если ты именно про Codex app)

**Не обязательно руками делать `git worktree add`** — Codex app умеет worktrees сам.

Твой “правильный” процесс тогда выглядит так:

1. **Открываешь один проект** (папку репозитория) в Codex app
2. На каждую параллельную задачу — **отдельный thread в режиме Worktree**
3. Codex создаёт отдельный worktree в detached HEAD (значит, можно запускать много потоков параллельно без “занятых” веток). citeturn7view0turn9view0
4. Завершаешь задачу одним из двух способов:
   - **A: Create branch here → commit/push/PR** (без локального checkout) citeturn7view0turn9view0
   - **B: Sync with local → Apply/Overwrite** (если нужно тестировать/запускать всё в твоей основной локальной копии) citeturn7view0turn9view0

Ключевая развилка простая:

- если ты можешь **проверять изменения прямо в worktree** (зависимости/инструменты есть) → Workflow A
- если у тебя “тяжёлый” проект и реально можно гонять dev-сервер/базу только в одном месте → Workflow B citeturn7view0

## 4) Практики “от опытных разработчиков” (как они советуют организовывать worktrees)

### 4.1. Держать worktrees в предсказуемом месте + понятные имена

Gérald Barré (Meziantou) формулирует практичные best practices:

- worktrees — в предсказуемой локации (например, sibling dirs),
- имена директорий — соответствуют веткам,
- регулярно чистить неиспользуемые worktrees. citeturn11view0

Это прям идеально ложится на “много агентов” (папка = поток/задача).

### 4.2. Понимать ограничение “одна ветка — один worktree”

GitHub Blog (пост про Git 2.5 от Michael Haggerty) хорошо объясняет механику:

- `git worktree` создаёт linked working tree,
- внутри linked worktree `.git` — это **файл-ссылка** на основной репозиторий,
- и Git **не позволяет** держать одну и ту же ветку checkout’нутой в двух worktrees одновременно. citeturn5view1

OpenAI в своих docs это же ограничение подчёркивает и объясняет, почему оно существует, и приводит типичную ошибку `fatal: '<branch>' is already used by worktree ...`. citeturn9view0

### 4.3. Detached HEAD как “режим песочницы”

Официальный мануал Git прямо рекомендует detached-worktree для тестов/экспериментов, чтобы не мешать основной разработке. citeturn5view0\
Codex app делает именно так “по умолчанию” (detached HEAD), чтобы можно было поднимать много worktrees без хаоса в ветках. citeturn7view0turn9view0

### 4.4. “Продвинутый” стиль: bare clone + worktrees (если ты реально живёшь в worktrees)

Safia Abdalla описывает workflow, где:

- есть “центральная” bare-копия репо (только git-данные),
- а рядом — worktrees (main, feature-1, feature-2…),
- и отдельно упоминает нюансы с remote-tracking и необходимость настроить fetch refspec в bare clone. citeturn10view0

Это круто, но я бы считал **опциональным**: для Codex app обычно достаточно его встроенной схемы.

## 5) Практический чек-лист “чтобы не наступать на грабли” (под твой кейс)

1. **Один агент = один worktree** (один тред Worktree в Codex). citeturn7view0
2. Не пытайся сделать так, чтобы **одна и та же ветка была checkout’нута** одновременно в разных местах. Если хочешь параллельные агенты на одной базе — пусть они работают в detached HEAD и потом синкаются/выливаются в ветку. citeturn9view0turn5view0
3. Если ты хочешь **проверять код локально в своём основном checkout** — чаще всего выбирай **Sync with local (Apply)**, а не “Create branch here”, чтобы не упереться в блокировку ветки. citeturn9view0
4. Следи за диском: каждый worktree — это отдельные файлы + возможно зависимости/кэши; Codex может чистить старые worktrees и хранит snapshot. citeturn9view0
5. Знай, где они лежат: по умолчанию это `~/.codex/worktrees` (через `$CODEX_HOME/worktrees`). citeturn8view0turn9view0

## 6) Если хочешь управлять “ручными” worktrees и открывать их в Codex app

Иногда удобно самому создать папку-worktree и открыть её в Codex Desktop.

Пример (внутри основного репо):

```bash
mkdir -p ../worktrees

# отдельная ветка под агента
git worktree add -b agent/auth ../worktrees/agent-auth origin/main

# или песочница без ветки (detached)
git worktree add --detach ../worktrees/sandbox-try
```

Механика `-b`/detached и то, что worktree можно привязать к существующей ветке/коммиту — в официальной доке Git. citeturn5view0

А чтобы быстро открыть конкретную папку в Codex Desktop из терминала, в docs есть `codex app <PATH>` (macOS). citeturn13view2

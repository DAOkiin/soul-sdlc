## 2) IEEE 12207: какие элементы стоит забрать в «лёгкий режим»

### 2.1. Скелет фаз (что именно компрессируем в итерации)

IEEE 12207 раскладывает жизненный цикл на фазы от требований до acceptance support (в таблице у Rico это «12 фаз»).【19:4†cs460 ieee12207.pdf†L72-L85】

В “лёгком итерационном режиме” вы **не делаете эти фазы как водопад**, вы берёте их как **чек-лист типов работы**, которые должны случиться хотя бы в мини‑виде в рамках итерации:

- requirements (что строим и как поймём, что оно “met”),
- architecture/design,
- implementation,
- integration,
- qualification/testing,
- (позже) installation/support.

### 2.2. Walkthrough vs Inspection — идеальная пара для agent‑development

IEEE чётко различает:

- **Walkthrough**: «неструктурированная встреча» для “публичности” идей; комментарии приветствуются, но нет обязательства внедрять фидбек.【19:11†cs460 ieee12207.pdf†L1-L10】
- **Inspection**: «структурированная нейтрально фасилитируемая встреча», цель — найти дефекты; **все дефекты должны быть исправлены** (и это ключ).【19:11†cs460 ieee12207.pdf†L11-L19】

Для агентской разработки это переводится очень просто:

- **Walkthrough** = быстрый async‑review спецификации/дизайна в issue/PR (вы +, при желании, Codex review как второй взгляд).
- **Inspection** = строгий PR‑гейт: тесты/линтеры/чеклист/нет регрессий/нет “висячих” требований.

### 2.3. Бэйзлайны как “контрольные точки” в git

IEEE определяет, что такое baseline, например:

- **Functional Baseline** — утверждённая конфигурационная документация, описывающая характеристики и верификацию, требуемую для демонстрации достижения этих характеристик.【19:1†cs460 ieee12207.pdf†L60-L68】
- **Allocated Baseline** — утверждённая “performance‑oriented” документация, распределяющая функциональные/интерфейсные характеристики по элементам (CI).【19:1†cs460 ieee12207.pdf†L69-L77】
- **Developmental configuration** — “эволюционирующая конфигурация” между allocated и product baselines.【19:1†cs460 ieee12207.pdf†L78-L86】
- **Test baseline** — подготовленные/ревьюнутые/утверждённые артефакты для qualification testing после успешной integration testing.【19:1†cs460 ieee12207.pdf†L87-L95】
- **Product baseline** — утверждённая техдокументация для production/deployment/support фаз.【19:1†cs460 ieee12207.pdf†L96-L104】

В вашем SDLC это можно реализовать **очень лёгко**: не отдельными “оборнными” документами, а **git tags + checklist‑signoff в `docs/iterations/<id>/reviews.md`**.

### 2.4. Что считать “SRS / SAD / TVPL / TVRR” без бюрократии

IEEE даёт “purpose” ключевых артефактов:

- **SRS**: «specify requirements … and the methods … to ensure each requirement has been met».【77:4†cs460 ieee12207.pdf†L9-L16】\
  → у вас это **global\_user\_stories.md + acceptance критерии/AT**.
- **SAD**: описывает “item-wide design decisions” и архитектуру, включая “concept of execution” и ограничения ресурсов.【77:4†cs460 ieee12207.pdf†L33-L41】\
  → у вас это **`04_architecture.md` + ADR**.
- **TVPL (test/validation plan)**: описывает планы тестирования, среду, тесты и расписание тестовых активностей.【77:4†cs460 ieee12207.pdf†L68-L76】\
  → у вас это **`acceptance.md` + CI/тест‑стратегия**.
- **TVRR (test/validation results report)**: «provide a record of the qualification testing performed…».【77:7†cs460 ieee12207.pdf†L47-L54】\
  → у вас это **CI‑прогоны + release notes + ссылки на конкретные runs** (без отдельного отчёта).

## 3) SDLC v0 для агентской разработки (Lean 12207 + ваш traceability)

Ниже — процесс, который **прост**, но держит качество и параллельность.

### 3.1. Слои артефактов (что является “источником истины”)

**Global (долгоживущий, меняется медленно):**

- Vision / Needs / Jobs-Outcomes (AJTBD)
- Реестры требований: US / UC / NFR
- Glossary
- Evidence register (ссылки на чаты/аудио/исследования)

**Iteration (замораживается как baseline на итерацию):**

- выбранный scope (US/UC/NFR + метрики + IN/OUT)
- архитектура/модели для итерации
- acceptance сценарии (AT) и трассируемость
- план реализации (как доставляем)

**Decision (постоянно):**

- ADR‑решения с привязкой к требованиям и evidence

**Ops (позже, ближе к деплою):**

- install/runbook (это ваш SIP‑lite; IEEE описывает SIP как документ “как установить/подготовить к operational use”).【77:0†cs460 ieee12207.pdf†L22-L29】

### 3.2. Итерационный цикл (встроенный “V‑подход”)

1. **Scope selection (Design Input)**\
   Выбираете минимальный wedge/вертикальный срез (обычно 2–5 US + соответствующие UC + 1–3 NFR).
2. **Design Output**\
   Архитектура + контракты + модели (чтобы агенты могли параллелить).
3. **Implementation & Integration**\
   Агенты делают изменения в ветках, интегратор сливает через PR‑гейты.
4. **Verification (build it right)**\
   Тесты/линтеры/интеграционные прогоны.
5. **Validation (build the right thing)**\
   acceptance сценарии + реальная проверка ценности (пусть даже вручную в MVP).
6. **Learnings**\
   Что узнали → обновили global слой / добавили evidence / поправили roadmap.

## 4) Как сделать процесс “Codex‑friendly” (ветки, долгие задачи, AGENTS.md)

### 4.1. Что Codex реально читает и как этим управлять

Официальная документация Codex прямо говорит:

- Codex **читает `AGENTS.md` до начала работы** и собирает “instruction chain” (global инструкции + project инструкции по дереву директорий). citeturn1view0
- Есть механизм `AGENTS.override.md` и приоритет: более “глубокие” файлы переопределяют более общие. citeturn1view0
- Есть лимит на общий размер project‑инструкций (по умолчанию 32 KiB) и возможность настраивать fallback filenames в конфиге. citeturn1view0

Это идеально ложится на ваш подход “global vs iteration”:

- **Корневой `AGENTS.md`**: общие правила репозитория (качество, тесты, требования к PR).
- **`docs/iterations/<id>/AGENTS.md`** (опционально): правила только для текущей итерации (какие docs/ID важны, какой scope, какие запреты).
- **Локальные override** (опционально): если появятся разные подсистемы.

### 4.2. Параллельные ветки и “долгие” задачи: практичная схема

Codex в quickstart прямо рекомендует делать **git checkpoints до/после каждой задачи**, потому что агент может менять код. citeturn0search0

Для вас это превращается в правило:

- **Одна задача = одна ветка.**\
  Имя ветки: `agent/<ISSUE-ID>-<slug>` или `agent/<US-xxx>-<slug>`.
- **Любая ветка агента живёт через PR (можно draft).**\
  Долгие задачи: держите PR в draft и пушьте маленькими порциями.
- **Интегратор (вы) — единственная точка merge в main.**\
  Это резко снижает риск “LLM‑хаоса”.

### 4.3. “Definition of Ready” для задачи, чтобы агент работал продуктивно

Чтобы Codex мог “стрелять по веткам” без постоянных уточнений, задача должна быть “Ready for agent”. Минимальный пакет:

- ссылка на **US/UC/NFR IDs**
- “что считается готовым” (acceptance / тесты / критерии)
- какие файлы/папки трогать
- ограничения (не менять публичные контракты без ADR, не добавлять зависимости без разрешения и т.п.)

### 4.4. Codex: локально vs cloud и полезные фичи, которые влияют на процесс

- Codex умеет **навигацию по репо, редактирование файлов, запуск команд и тестов** (CLI/IDE/приложение). citeturn2view0
- **Codex app** ориентирован на **несколько агентов параллельно** и имеет **worktree‑поддержку и git‑функции** — это буквально ваш сценарий “несколько веток”. citeturn2view0
- Есть интеграция для code review в GitHub (`@codex review`). citeturn0search14

## 5) Как “начать весь процесс” — конкретный план (без лишних вопросов)

Ниже — максимально практичный «boot sequence», который соответствует вашему плану, но делает его более “железным” под агенты.

### Шаг A. Зафиксировать “входные двери” репозитория

1. **`README.md`** (корень):
   - что такое PAIP
   - как запустить dev
   - где лежит документация и “какой файл главный”
2. **`SDLC.md`** (корень):
   - короткое описание процесса
   - ссылки на подробный документ (ваш `_meta/sdlc.md`)
   - приложение: “Iteration Pack v0”
3. **`AGENTS.md`** (корень):
   - правила работы агентов/кодекса (обязательные команды, запреты, формат PR)

> Почему это важно: Codex реально использует `AGENTS.md` как постоянные инструкции. citeturn1view0

### Шаг B. Привести структуру доков к одному “источнику истины”

У вас сейчас `_meta/`, `product/`, `research/` в корне, но в текстах местами фигурирует `docs/...`.\
Сделайте один выбор:

- **Вариант 1 (рекомендую):** всё документальное — в `docs/` (а корень = код + входные файлы).
- **Вариант 2:** оставить как есть, но привести все ссылки к реальным путям.

Главное — чтобы **AGENTS.md и README.md** показывали агентам “истину”: куда смотреть за vision/US/UC/iteration.

### Шаг C. Сформировать Iteration Pack v0 (это ваш “appendix к SDLC.md”)

Создайте папку первой итерации, например:\
`docs/iterations/2026-02-mvp/`

И в ней минимально:

- `01_vision.md` — scope + метрики + IN/OUT
- `04_architecture.md` — архитектура + контракты
- `acceptance.md` — AT‑сценарии (TVPL‑lite)
- `traceability.md` — `US/UC/NFR → Design → AT`
- `reviews.md` — чеклисты baselines + sign‑off

### Шаг D. Разрезать MVP на “задачи для агентов”

Правило: **агентам отдаём только то, что можно сделать в ветке и проверить.**\
Примеры типов задач:

- “Добавить базовую модель данных/схему и миграции”
- “Сделать адаптер источника X с контрактом `RawArtifact`”
- “Сделать diff/dedup для типа Y + тесты”
- “Сделать уведомления + хранение истории”

Каждая задача получает:

- ссылку на US/UC/NFR
- ссылку на acceptance AT
- список файлов/папок для изменения
- “Definition of Done” для PR

### 6.1. `AGENTS.md` (корень репозитория)

```md
# AGENTS.md — инструкции для Codex/агентов в этом репозитории

Codex читает этот файл перед началом работы. Цель — чтобы изменения были предсказуемыми, тестируемыми и трассируемыми.

## Источник истины (обязательно читать перед работой)
1) Vision: docs/product/global_vision.md
2) Требования: docs/product/global_user_stories.md, docs/product/global_use_cases.md, docs/product/nfr.md
3) Глоссарий: docs/product/glossary.md
4) Текущая итерация: docs/iterations/<CURRENT>/ (01_vision.md, 04_architecture.md, acceptance.md, traceability.md, reviews.md)
5) SDLC: SDLC.md

Если файлы лежат не в `docs/`, используй путь из README.md.

## Рабочие соглашения
- Одна задача = одна ветка = один PR (draft разрешён).
- Не меняй глобальные IDs (US/UC/NFR/AT/ADR) и их смысл без явного указания в задаче.
- Не меняй публичные контракты/схемы/форматы без ADR (docs/adr/ADR-####-*.md).
- Не добавляй новые прод-зависимости без явного разрешения (комментарий в PR/issue).
- Не делай “рефакторинг ради красоты”, если это не цель задачи.

## Перед началом
- Сделай git checkpoint (коммит/тег) перед значимыми изменениями, чтобы можно было откатиться.
- Убедись, что понимаешь acceptance критерии для US/AT.

## Обязательные проверки перед PR
Укажи в PR:
- Какие US/UC/NFR закрываешь (IDs)
- Какие AT покрываешь (IDs)
- Как запустить проверки

Запусти локально (подставь реальные команды проекта):
- `make lint` или `npm run lint`
- `make test` или `npm test`
- (если есть) `make typecheck`

## Формат результата (в конце PR-описания)
- Summary: 3–7 bullets
- Evidence: команды/логи тестов + что проверено
- Risks: что может сломаться
- Follow-ups: что НЕ сделано и почему
```

### 6.2. `SDLC.md` (корень) — “front door” + приложение Iteration Pack

```md
# SDLC (v0) — процесс разработки

Этот файл — «входная дверь». Подробный SDLC: docs/_meta/sdlc.md (или _meta/sdlc.md — см. README).

## Цели
- Итерационная разработка (MVP → расширение).
- Трассируемость: OUT → US/UC/NFR → Design → AT → Evidence.
- Максимум параллельности через агентов при сохранении качества через PR-гейты.

## Основные правила
1) Global требования живут отдельно от итераций.
2) Итерация — это “Design Input → Design Output → Validation”.
3) Все изменения кода проходят через PR + тесты.
4) Любое существенное архитектурное решение фиксируется ADR.

## Гейты (Baselines)
- Requirements Baseline: scope итерации + acceptance/traceability заполнены.
- Design Baseline: архитектура/модели/контракты готовы, traceability связывает дизайн с требованиями.
- Validation Baseline: AT определены/покрыты, есть план прогона.

## Роли (минимум)
- Maintainer/Integrator (человек): принимает scope, мерджит PR, закрывает baselines.
- Agents (Codex): выполняют задачи в ветках по правилам AGENTS.md.

## Приложение A — Iteration Pack v0 (обязательные файлы)
В каждой итерации создаётся папка: `docs/iterations/<id>/` и файлы:
- 01_vision.md
- 04_architecture.md
- acceptance.md
- traceability.md
- reviews.md
- 07_mvp_plan.md (опционально, но полезно)

Содержимое и шаблоны — см. ниже.
```

### `reviews.md` (чеклист baselines + walkthrough/inspection)

```md
# Reviews & Baselines — <iteration_id>

## Requirements Baseline (Design Input)

- [ ] Для каждого US есть хотя бы один AT в acceptance.md
```

## 1) “Много часов” чаще достигают не одним непрерывным ответом, а **длинным циклом работы агента**

В Codex CLI по умолчанию агент делает кусок работы → отчитывается → ждёт следующего ввода. Это прямо описывают как проблема/особенность: “делает chunk и репортит, а я хочу чтобы он работал долго без постоянных остановок” — люди обходят это тем, что дают команду “continue”/следующее сообщение в очереди. citeturn0search1turn0search13

То есть “он работает 5 минут и останавливается” — это очень типичный режим, не обязательно “неправильная настройка”.

## 2) Официальные куски, которые реально помогают именно для многочасовой работы

### Compaction = чтобы сессия жила долго и не упиралась в контекст

В официальном Codex Prompting Guide упоминается “first-class compaction support” — идея в том, что агент может “сжимать” историю и продолжать многочасовые рассуждения/диалоги без постоянного рестарта с нуля. citeturn0search7

### Extra High reasoning effort (xhigh) = для “не важно по latency, важно по качеству”

OpenAI отдельно вводили Extra High (“xhigh”) режим рассуждения для Codex-Max, именно как режим “думает дольше”. citeturn0search5

### AGENTS.md / project instructions = чтобы агент не тратил время на переобъяснения

В Advanced Configuration описано, что Codex читает `AGENTS.md` и родственные файлы как проектные инструкции, и это подхватывается на старте сессии (и на практике сильно снижает “дергание” и уточняющие вопросы). citeturn0search15

## 3) Практический “manual” от людей: **tmux/screen + несколько панелей/агентов**

Самый частый паттерн: запускать Codex CLI внутри `tmux`, чтобы:

- сессия не умирала при разрыве терминала/сна ноутбука,
- можно было “прикрепиться” обратно,
- можно было держать параллельные панели (сервер, тесты, codex).

Это прямо обсуждают как типичный воркфлоу пользователи (в т.ч. совет “если нужен multitasking — tmux”). citeturn0search10\
Есть и свежая статья с конкретным подходом “гонять Codex агентов параллельно через tmux”. citeturn0search2

> Важно: в репозитории openai/codex даже есть запрос на “background terminal sessions” (ре-attach как у Claude Code) — то есть люди явно пытаются превратить это в долгоживущие терминальные джобы. citeturn0search0\
> И обратная сторона: иногда долгие tmux-сессии клинятся из-за “low-credit picker”, это тоже описывают как проблему именно для long-running workflows. citeturn0search14

## 4) Codex App (macOS) как “официальный” путь к параллельным/долгим задачам

OpenAI продвигают Codex app как “command center for agents” и подчёркивают, что оно подхватывает историю/конфиг из CLI/IDE, а также ориентировано на параллельные агентные воркфлоу. citeturn0search9turn0search21\
Если тебе нужно именно “поставил и пусть фигачит часами”, app часто ближе к этому UX, чем CLI.

## 5) Как люди формулируют промпт, чтобы Codex реально “работал долго” (шаблон)

Это не “секретная настройка”, а дисциплина задания:

- **Определи “условия остановки”**: “Остановись только если: (а) нужны секреты/доступы, (б) тесты падают и ты не можешь починить за 3 попытки, (в) требуется выбор из нескольких UX-вариантов — предложи 2 и выбери один по умолчанию.”
- **Сделай план → выполняй по чеклисту**: “Сначала составь план из 8–15 шагов, потом выполняй шаги молча, логируй только важные решения.”
- **Артефакты прогресса**: “Веди PROGRESS.md, обновляй после каждого крупного этапа.”
- **Команды**: “Запускай тесты/линтер после каждого логического блока.”
- **Ограничь болтовню**: “Не делай частых апдейтов. Пиши отчёт раз в N этапов или при блокере.”

Судя по жалобам в issue “Can’t do long running tasks”, без таких явных правил Codex склонен “делать кусок → отчитываться”. citeturn0search1

## Как заложить это в новый репозиторий под твою цель (без лишней философии)

### 1) Сделай AGENTS.md коротким “маппингом” (а не мануалом)

Опираясь на Harness engineering: AGENTS.md должен быть **картой**: что где лежит, какие команды считать “истиной”, где SDLC-правила, где лог решений. citeturn2view0turn0search0

Минимально:

- “как запускать тесты/линтер/форматтер”
- “где правила SDLC”
- “где текущая итерация и задачи”
- “как вести decision log и привязывать к коммитам”

### 2) Храни SDLC как “system of record” в docs/

Так же, как в статье OpenAI: `docs/` — источник истины, а AGENTS.md — указатель. citeturn2view0

Твоя терминология уже подходит:

- верхнеуровневый файл (map)
- файл итерации
- файл задачи
- история/короткие записи “что происходило”

### 3) Для “работает пока не закончит” — заведи **план-док (PLANS.md / ExecPlan)** и правило “план обязателен”

У OpenAI есть отдельный рецепт про PLANS.md и многочасовую работу через “ExecPlan”. citeturn0search10\
Суть для твоего кейса: агент не “делает кусок и останавливается”, а работает по плану, обновляя артефакты (план/лог) пока не выполнит “definition of done”.

### 4) “Лог решений с привязкой к коммитам” как обязательный артефакт

Технически это можно сделать так, чтобы агент *сам* всегда оставлял след:

- `docs/decisions/DECISIONS.md` (или per-iteration log), где каждый пункт имеет:
  - decision id
  - краткое решение
  - ссылка/хэш коммита
  - “почему так” (1–3 bullets)
  - “альтернативы” (если были)

Чтобы агент реально делал это стабильно, зафиксируй правило в инструкциях (AGENTS.md → ссылка на документ SDLC/логирования) и в “Definition of Done”.

### 5) Если ты хочешь именно **долгоживущую** сессию “между ходами”

Посмотри гайд **Use Codex with the Agents SDK**: там Codex CLI поднимается как MCP-сервер с `codex()` / `codex-reply()` и идея ровно про “keeps Codex alive across multiple agent turns”. citeturn0search3\
Это полезно, если ты хочешь, чтобы управляющий процесс мог “докручивать” агента много ходов подряд без ручного “continue”.

- **Контекст текущей задачи** — в `docs/tasks/CURRENT_TASK.md` (и валидатор следит, чтобы файл не разрастался).
- **SDLC правила** — в `docs/SDLC.md`.
- **Итерация** — `docs/ITERATION.md` + короткий лог `docs/history/ITERATION_LOG.md`.
- **История задач** — `docs/history/TASK_LOG.md`.
- **Лог решений с привязкой к коммитам** — `docs/decisions/DECISIONS.md`.
- **Состояние** — `state/*.json`.
- Мини‑инструменты:
  - `tools/validate_repo.py` — проверки структуры/JSON/размера CURRENT\_TASK
  - `tools/harness.py` — удобные команды (new-task / start-task / log-decision / complete-task)

## Как сразу запустить разработку (macOS)

1. Распакуй архив, зайди в папку:

```bash
cd agent-sdlc-harness
```

2. (Рекомендуется) инициализируй git и сделай первый коммит:

```bash
git init
git add .
git commit -m "chore: bootstrap harness [TASK-0001]"
```

3. Проверь, что каркас “живой”:

```bash
make check
```

Если без `make`:

```bash
python3 tools/validate_repo.py
python3 -m unittest discover -s tests -p "test_*.py" -q
```

4. Открой папку репозитория в **Codex Desktop**.
